# Scientex CLI Command Reference

This page contains the longer command catalog. The README keeps only quick-start and high-level guidance.

All commands support `-f json` for machine-readable output.

## Auth

```bash
scitex login
scitex status
scitex logout
```

`scitex login` 会输出飞书认证链接，并在前台持续轮询 token。用户完成浏览器授权后，命令保存 token 并报告成功；保持该命令运行直到流程结束。

## Files

```bash
scitex files upload input.bin
```

`files upload` 返回可嵌入任务或公开 Tool Catalog 参数的 FileFieldRef。需要把该对象保存到 JSON 时使用 `-f json`；不要从本机路径、URL 或 storage key 手工构造它。需要在创建任务时直接附带文件时，也可以继续使用 `tasks create --file-field field_key=path`。

```bash
scitex project tashan seed lots movements <LOT_ID>
scitex project tashan seed lots reservations <LOT_ID>
scitex project tashan seed lots reserve <LOT_ID> --weight-g <DECIMAL_G> [--purpose TEXT] [--experiment-ref REF] --yes
scitex project tashan seed reservations release <RESERVATION_ID> --yes
scitex project tashan seed lots checkout <LOT_ID> --weight-g <DECIMAL_G> [--reservation <RESERVATION_ID>] [--purpose TEXT] [--experiment-ref REF] --yes
scitex project tashan seed lots transfer <LOT_ID> [--location-id <LOCATION_ID>] [--site TEXT] [--location-text TEXT] [--note TEXT] --yes

```

`batches download-template` only downloads the XLSX template frozen for that batch. It streams into a temporary sibling and will not overwrite an existing target without `--force`. `import-manifest` accepts only a non-empty readable `.xlsx`, sends it under multipart field `file`, and returns an asynchronous import task rather than a completed import. The legacy `seed stocks` view remains read-only migration compatibility; use `seed lots` for formal balances and the immutable movement/reservation ledger. All lot weights are decimal strings in grams with at most four decimal places; lot writes require `--yes` in non-interactive use.

## Tasks

Task instances have three distinct views: Lab tasks (`/lab/tasks`) for the current lab, Platform tasks (`/tasks`) for platform administrators across labs, and My Tasks (`/staff/tasks`) for task stages assigned to the current staff member. The same task can appear in all three views.

```bash
# Lab tasks — normal lab member view, scoped to current lab or --lab-id.
scitex tasks types
scitex tasks types --lab-id <LAB_ID>
scitex tasks types --search "tm"
scitex tasks types --search "tm" --category compute --limit 20
scitex tasks type <TASK_TYPE_ID>
scitex tasks type <TASK_TYPE_ID> --lab-id <LAB_ID>

scitex tasks create task.json
scitex tasks create task.json --lab-id <LAB_ID>
scitex tasks create task.json --file-field plasmid=plasmid.dna

scitex tasks create-workflow workflow.json
scitex tasks create-workflow workflow.json --lab-id <LAB_ID>

scitex tasks list
scitex tasks list --lab-id <LAB_ID>
scitex tasks get <TASK_ID>
scitex tasks get <TASK_ID> --lab-id <LAB_ID>
scitex tasks part <TASK_ID> <PART_ID>
scitex tasks part <TASK_ID> <PART_ID> --lab-id <LAB_ID>
scitex tasks part <TASK_ID> <PART_ID> --timezone Asia/Shanghai
scitex tasks part-reschedule <TASK_ID> <PART_ID> --release-at 2026-08-01T09:00:00+08:00 --timezone Asia/Shanghai --reason "move to next shift" --yes
scitex tasks part-reschedule <TASK_ID> <PART_ID> --delay <DEPENDENCY_ID>=1:week --reason "allow recovery" --yes
scitex tasks part-reschedule <TASK_ID> <PART_ID> --release-immediately --reason "schedule cleared" --yes

scitex tasks documents <TASK_ID>
scitex tasks download-document <DOCUMENT_ID> [output.bin]
scitex tasks upload-field <TASK_ID> file.bin field_key

scitex tasks results <TASK_ID>
scitex tasks results <TASK_ID> --lab-id <LAB_ID>
scitex tasks download-results <TASK_ID> [OUTPUT_DIR]
scitex tasks confirm <TASK_ID>
scitex tasks reject <TASK_ID> --reason "needs rerun"

# My Tasks — only task stages assigned to the authenticated staff member.
scitex tasks my list --search "sample qc" --exclude-status completed
scitex tasks my get <ASSIGNMENT_ID>
scitex tasks my status <ASSIGNMENT_ID> <pending|in-progress|completed>
scitex tasks my submit-result <ASSIGNMENT_ID> result.json
scitex tasks my complete <ASSIGNMENT_ID> result.json [--feedback feedback.json]
scitex tasks my upload-field <TASK_ID> file.bin field_key --visibility lab-and-staff
scitex tasks my documents <TASK_ID>
scitex tasks my download-document <DOCUMENT_ID> [output.bin]
```

`tasks types` always searches enabled, submit-able task definitions in the current lab (or `--lab-id`). It accepts `--search`, `--category`, `--skip`, and `--limit` together and returns lightweight selection summaries rather than schemas or administrative configuration. After choosing a candidate, use `tasks type <TASK_TYPE_ID>` to retrieve its submission schema, output schema, and user-visible document metadata before creating a task. This is not the platform administrator `/task-types` catalog. `tasks get <TASK_ID>` also resolves each visible part's task type and displays its user-facing input requirements; JSON output adds them under `input_requirements` without removing task fields.

`tasks part` includes lab-visible runs, incoming dependencies, schedule-change history and schedule fields. A `LOCKED` part with `not_before_at` is waiting for its release boundary; `READY` is already released and waiting for assignment/execution. `part-reschedule` only changes a still-locked stage and needs interactive confirmation (or `--yes`). It requires a non-empty `--reason`; absolute time is RFC3339 with an offset and a valid IANA `--timezone`; each dependency delay uses `DEPENDENCY_ID=VALUE:minute|hour|day|week`.

There is currently no lab-scoped workflow-detail endpoint. Lab members should use `tasks get`, `tasks part`, and `tasks results`; `admin tasks workflow` is not a fallback for a permission-denied lab request.

员工正常完成阶段时优先使用 `tasks my complete`，它会原子提交结果、完成 assignment 并解锁后续阶段。`submit-result` 和 `status` 保留给分步处理场景；不要把两条命令拼成普通完成流程。

两个结果命令的 `result.json` 默认直接写该阶段 `output_schema` 定义的输出对象，例如：

```json
{
  "checked_samples": 12,
  "passed": true
}
```

CLI 会发送 `{ "output_data": <result.json 内容> }`；`--feedback feedback.json` 会在
同一请求顶层写入 `document_feedback`。为了兼容已有脚本，也可传完整
`TaskResultCreate` 信封。若输出 schema 自身含有 `output_data`、`comment` 或
`document_feedback` 顶层字段，请显式使用 `{ "output_data": { ... } }` 信封以消除歧义。

## Published Tool Catalog

```bash
scitex tool search [--query TEXT] [--domain DOMAIN] [--family FAMILY] [--tag TAG] [--skip 0] [--limit 50]
scitex tool show <TOOL_KEY>
scitex tool validate <TOOL_KEY> --version <TOOL_VERSION_ID> --input input.json
scitex tool run <TOOL_KEY> --version <TOOL_VERSION_ID> --input input.json [--title TEXT] [--description TEXT] [--lab-id <LAB_ID>] --yes
scitex tool rerun <TASK_ID> <PART_ID> <RUN_ID> [--lab-id <LAB_ID>] --yes
scitex tool artifact-preview <TASK_ID> <PART_ID> <RUN_ID> <ARTIFACT_INDEX> [--lab-id <LAB_ID>]
```

Only published user-safe Tool Catalog metadata is exposed. `run` validates the input again in the same invocation and will not submit if validation fails; it and `rerun` require interactive confirmation or `--yes` for non-interactive use. Select the exact published version ID from `tool show`; do not replace it with a newer version. For `format: file` parameters, use the complete FileFieldRef returned by `scitex files upload -f json`; the CLI rejects a local path, URL, bare storage key, or incomplete reference shape. Tool dispatch is asynchronous; use the returned task and part IDs to inspect status. Artifact previews are bounded server text previews, not raw storage access.


- `admin task-types` 管理平台任务定义目录；普通 Lab 用户查找可提交定义时仍使用 `tasks types --search`。
- `admin tasks` 是跨 Lab 的平台全局任务视图。旧的顶层 `tasks workflow/update/update-file` 仅隐藏保留兼容，新流程不要再使用。
- They do not create executable lab tasks; use `scitex tasks create` or `scitex tasks create-workflow` for task execution.
- Task type staff binding is catalog configuration; task instance assignment still uses workflow `assignee_ids`.
- If the backend rejects the request with a permission error, the CLI reports that the current account lacks permission for the admin operation.

### Task Creation Notes

- Use `scitex tasks create` for single-stage tasks with one root `task_type_id`.
- Use `scitex tasks create-workflow` for multi-stage tasks.
- Workflow payloads should use `parts[*].task_type_id` instead of a root `task_type_id`.
- Each workflow part must have a unique `client_key`.
- Dependencies should reference `client_key` values.

Workflow example:

```json
{
  "title": "Tm compute then QC review",
  "parts": [
    {
      "client_key": "tm_compute",
      "name": "Tm compute",
      "task_type_id": "compute-task-type-uuid",
      "input_data": {
        "sequence": "ATGGTCTCAGGAAACCTAGACCCAGAAAAACACGAATGG"
      },
      "sort_order": 10
    },
    {
      "client_key": "qc_review",
      "name": "QC review",
      "task_type_id": "staff-task-type-uuid",
      "input_data": {
        "sample_ids": ["S001", "S002"]
      },
      "assignee_ids": ["user-uuid-1"],
      "sort_order": 20
    }
  ],
  "dependencies": [
    {
      "prerequisite_client_key": "tm_compute",
      "dependent_client_key": "qc_review",
      "condition_type": "completed"
    }
  ]
}
```

### Task Inspection Notes

- Platform administrators can use `scitex admin tasks workflow <TASK_ID>` to inspect global workflow structure, parts, dependencies, and assignments. Lab members use `scitex tasks get`, `scitex tasks part`, and `scitex tasks results`.
- `scitex tasks results <TASK_ID>` is workflow-aware:
  - single-stage compute tasks show compute output
  - single-stage staff tasks show submitted results
  - workflow tasks show results grouped by part, using `part.output_data` for compute stages and submitted results for staff stages
